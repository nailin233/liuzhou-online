## 3. 已核实正确的部分

以下结论用于说明审查覆盖了哪些点，避免 Codex 重复排查。

### 3.1 坐标轴与东西南北

`projection`（`geography.ts:22-33`）返回 `[(lon−lon0)·east, (lat0−lat)·north]`：

- 第一个分量为东向米数，`east = a·cosφ/W`，即卯酉圈曲率半径乘 cosφ，公式正确。
- 第二个分量为**南向**米数，`north = a(1−e²)/W³`，即子午圈曲率半径，公式正确。变量名叫 `north`，但输出的符号是"向南为正"。

由此得到场景坐标系：+X = 东，+Y = 上，+Z = 南。这是右手系（东 × 上 = 南），与 Three.js 惯例"北 = −Z"一致。

三类要素都落在同一坐标系上：

| 要素 | 变换链 | 最终坐标 |
| --- | --- | --- |
| 道路 `tile.ts:124-125,44-51` | `Vector2(东, 南)` → `(x, 0, y)` | (东, 0, 南) |
| 林地 `tile.ts:19-20,140-141` | `Vector2(东, 北)` → 绕 X 轴 −90° | (东, 0, −北) = (东, 0, 南) |
| 建筑 `tile.ts:146-150` | `Vector2(东, 北)`，挤出沿 +Z → `rotateX(−π/2)` | (东, 高度, 南) |

对 `rotateX(−π/2)` 的推导：(x, y, z) → (x, z, −y)。顶面 z = depth 映射到 y = depth，底面在 y = 0，方向正确。

### 3.2 道路条带朝向

`roadGeometry`（`tile.ts:29-66`）：以沿 +X 的路段为例，左法线 (0, 1)，三角形 `(a, a+2, a+1)` 的三维顶点为 (0,0,1)、(1,0,1)、(0,0,−1)，叉积法线为 (0, 2, 0)，朝上。`computeVertexNormals` 得到的光照法线正确，接收阴影正常。

转角处理：斜接长度上限为半宽的 2 倍（`Math.max(0.5, …)`，`tile.ts:43`），即转角超过 120° 时该顶点处会变窄，属设计取舍。180° 折返时 `before + after = 0`，`normalize()` 对零向量保持为零，随后 `copy(after)`，不会产生 NaN。

### 3.3 轮廓挤出

- `ExtrudeGeometry` 内部会统一外环与内环的绕序，OSM 外环顺时针或逆时针都能正确三角化，`shape.holes` 正确承载内环（`tile.ts:23-24`）。
- 材质组 0 为顶底盖、组 1 为侧面，`[roof, wall]` 对应正确（`tile.ts:151`）。
- `EdgesGeometry(solid, 24)` 在 `rotateX` 之后创建，描边与实体对齐。

### 3.4 瓦片裁剪平面

Three.js 保留 `n·p + c ≥ 0` 的片元。四个平面（`tile.ts:94-99`）分别保留 x ≥ left、x ≤ right、z ≥ top（北边界）、z ≤ bottom（南边界），与地块 `BoxGeometry` 的范围一致。投影对经纬度是线性的，所以 bbox 投影后仍为矩形，与要素投影一致。

### 3.5 俯视视角与罗盘

- 俯视位置 `(0, 690, 0.01)`（`main.ts:81`）：相机位于 target 正南 1 cm。推导得屏幕右 = +X（东），屏幕上 = −Z（北），"正北俯视"成立。OrbitControls 的极角 1.45×10⁻⁵ rad 大于其内部 EPS（10⁻⁶），不会被钳制成不稳定状态。
- 罗盘 `rotate(getAzimuthalAngle())`（`main.ts:177`）：方位角 θ 从 +Z 向 +X 计，相机在 θ 时，北方在屏幕上相对"上"顺时针偏 θ；CSS `rotate` 正值为顺时针，符号正确。前提是指针元素在未旋转时指向上方，这取决于未提供的 `style.css`/`index.html`。
- WASD 平移（`main.ts:110-113`）：`forward × up` 得到屏幕右方向，A/D 方向正确；俯视时 forward 由 0.01 偏移保证非零。

### 3.6 灯光

太阳位于 (−280, 440, −170)，即西北方、高度角约 53°（`main.ts:22`）。这符合制图惯用的西北光源，不是柳州的真实日照（北纬约 24° 处，高度角 53° 时太阳方位约在 83° 或 277°，不会出现在 301°）。这一点不算缺陷，但阴影方向不应被当作真实日照解读，建议在 `docs/` 中注明。

## 4. 阻断缺陷

### B1：楼高占位未标识

**位置**

- `geography.ts:57`：无 `height`、无 `building:levels` 时返回 `{ meters: 10, source: 'placeholder' }`。
- `tile.ts:145-157`：只使用 `height.meters`，`height.source` 没有被读取。三种来源的建筑使用同一套 `roof`/`wall`/`stroke` 材质。
- `main.ts:48`：HUD 只显示建筑总数。

**影响**

Issue 正文说明当前 34 栋建筑楼高全部未知，所以场景里的每一栋建筑都是 10 m 的统一高度，而画面上看不出这是占位值。其中三栋被标注为"东都大厦""工贸大厦""聚宝大厦"（`tile.ts:158-162`），标签悬在 13 m 处，会被读成这些大厦的真实体量。这违反 `docs/requirements.md` 第 4 条"真实地理信息缺失时必须显示缺失"和 `AGENTS.md` 第 6 条。

**复现**

任何视角下打开页面即可看到：所有建筑等高、同色，没有任何界面元素说明高度来源。

**修复接口与验收项（交给 Codex）**

不新增需求，只要求把已经计算出的 `source` 呈现出来：

1. `loadMap` 返回值增加按来源的计数，例如 `counts.heightSource: Record<'height' | 'levels' | 'placeholder', number>`，以 OSM ID 去重，口径与 `counts.buildings` 相同。
2. `source === 'placeholder'` 的建筑使用可区分的外观（例如单独的墙面/顶面颜色或半透明），`levels` 来源也与 `height` 来源区分，因为"层数 × 3 m"同样是估算。
3. HUD 显示"楼高未知 N / 总数"，并给出图例说明占位高度为 10 m、不代表实际。
4. 带名称标签的建筑若高度为占位值，标签需附带"楼高未知"或同等提示。

验收：在当前数据下，HUD 显示楼高未知 34/34；34 栋建筑均为占位外观；`buildingHeight` 的单元测试覆盖三种来源（见 7.1）。

## 5. 后续改进

### P1-1：步行道与车行道共面闪烁

**位置**：`tile.ts:130-132`。`walk`（0xc5b186）与 `road`（0xb5a58a）两种颜色的网格都放在 y = 0.16。

**影响**：`highway=pedestrian` 与其他道路在节点处相交时，两个网格在重叠区域完全共面，颜色不同，任何距离下都会出现 Z-fighting。共面时提高深度精度也无济于事。同材质道路之间的重叠颜色相同，闪烁不可见，可以忽略。

**复现**：在步行道与车行道相交的节点附近，以较低视角缓慢旋转相机。

**建议**：同一高度上用 `polygonOffset` 或 `renderOrder` 区分等级，或给步行道一个单独的高度层。

### P1-2：深度精度（需渲染确认）

**位置**：`main.ts:59` 近平面 0.5 m、远平面 6000 m；地表层高度为地块顶 0、林地 0.08（`tile.ts:142`）、道路 0.16、重点道路 0.27（`tile.ts:132`）。

**计算**：24 位深度缓冲下，视深 d 处的可分辨间距约为 d² / (near · 2²⁴)。

| 视深 d | 可分辨间距 |
| --- | --- |
| 761 m（横屏默认全景，target 处） | 约 0.07 m |
| 1100 m（默认全景下地块远端，假设地块半宽约 390 m） | 约 0.14 m |
| 1650 m（`maxDistance`） | 约 0.32 m |

林地与地块顶、道路与林地之间只隔 0.08 m，在默认全景的远半部分已低于可分辨间距，林地和道路边缘可能闪烁。竖屏时 `fit` 最大 2.6，相机会被推到 `maxDistance`，问题更明显。

**建议**：把近平面提高到 2 m 左右（1100 m 处约 0.036 m），并配合 `polygonOffset`。近平面提高后，相机最低高度需要相应抬升：当前 `minDistance = 12` 加 `maxPolarAngle = 0.485π` 时，相机只比 target 高约 0.57 m，近平面 2 m 会在画面底部裁掉地面。如果 Codex 截图显示默认视角已出现闪烁，本项升为阻断。

### P1-3：Q/E 让 target 离开地面

**位置**：`main.ts:123-129`。`move.y` 同时加到 `controls.target` 和 `camera.position` 上；`main.ts:127` 只保证相机 y ≥ 2，没有约束 target。

**影响**：

- 默认全景下按住 Q，相机下降到 y = 2 时 target 已到约 −530 m。此后用滚轮缩放，相机会朝地下的 target 前进并穿过地面。地面 `PlaneGeometry` 只有正面（`main.ts:37-41`），从下方看不可见。
- 按住 E 没有上限，相机越过远平面 6000 m 后整个地图消失。
- 点击"街区全景"可以恢复，所以不列为阻断。

**复现**：点击"街区全景" → 按住 Q 约 3 秒 → 向前滚动滚轮。

**建议**：Q/E 只改变相机高度（通过极角或距离），target 的 y 固定为 0；或在每帧 `controls.update()` 之后同时钳制 target.y 与 camera.y。

### P1-4：描边与阴影越过瓦片边界（依数据）

**位置**：`tile.ts:112-116` 的 `stroke` 没有设置 `clippingPlanes`；`surface()` 的材质没有设置 `clipShadows: true`（`tile.ts:100-105`）。

**影响**：如果某栋建筑或某块林地跨越 bbox，墙面会被裁掉，但描边线完整保留，会在地块外悬空；被裁掉部分仍然投射阴影。是否可见取决于数据中有没有跨 bbox 的建筑（见 6.3）。名称标签位置取自未裁剪几何的包围盒中心，也可能落在地块外。

**建议**：`stroke` 使用同一组 `clippingPlanes`，`surface()` 增加 `clipShadows: true`。

### P1-5：道路宽度为估算值

**位置**：`geography.ts:60-71`。只有 OSM `width` 标签存在时才使用实测宽度，否则按等级查表，未列出的等级（包括 `primary`、`residential`、`unclassified`）一律 6 m。

**影响**：道路中心线来自 OSM，但宽度基本是估算。与 B1 同理，界面应说明宽度为按等级估算。另外，若数据中出现 `primary`，它会比 `secondary`（12 m）还窄，等级关系颠倒。

**建议**：图例注明"道路宽度按等级估算"；表中补齐常见等级。

## 7. 测试与验收建议（交给 Codex）

### 7.1 单元测试（纯函数，不需要浏览器）

- `projection`：以 manifest 原点为参照，经度 +0.001° 得到 x > 0、y ≈ 0；纬度 +0.001° 得到第二分量 < 0（向北为负 Z）；数值与 WGS84 曲率半径公式的误差小于 0.01 m。
- `buildingHeight`：`height="15 m"` → 15 / `height`；`building:levels="4"` → 12 / `levels`；无标签 → 10 / `placeholder`；`height="0"` 回落到 levels。
- `surfaceRoad`：`tunnel=yes`、`layer=-1`、`highway=steps`、`highway=platform`、`location=underground` 返回 false；`tunnel=no` 返回 true。
- `roadGeometry`：直线两点、宽 10 时顶点 z 偏移为 ±5，所有面法线 y > 0；重复点被去除；180° 折返不产生 NaN。

### 7.2 对 `tests/explore.playwright.js` 的意见

- 只断言视图"发生了变化"，没有断言方向正确。"正北俯视"只检查 `aria-pressed`，无法发现北向错误。建议把相机状态推导抽成纯函数后做单元断言，或由 Codex 截图核对。
- 返回了 `roads`、`buildings` 计数但没有断言，建议断言等于 30 和 34（与数据审计一致）。
- 缩放检查依赖"东都大厦"标签可见。标签被重叠规则隐藏（`main.ts:163-171`）时 `transform` 不会更新，测试会误报失败；如果数据中没有该名称，`evaluate` 会等待超时。
- 没有覆盖 P1-3：建议增加"按住 Q 后滚轮缩放，相机 y 始终 ≥ 地面"的检查。
- `FPS · WebGL` 只说明 `requestAnimationFrame` 在运行，不能证明画面有内容。像素级确认依赖 Codex 截图。
- 该脚本通过 `playwright-cli run-code` 运行，不属于 `npm test`。`docs/requirements.md` 的验收条件仍是 `npm test` 与 `npm run build` 通过。
