## 交接原则
1. 上游 Agent 必须在 PR 合并后才算完成
2. 下游 Agent 依赖的文件必须在 main 分支
3. 所有引用的数据必须有明确来源
4. 交接通过 GitHub Issue 的 "Depends-On" 声明

## Agent 能力边界

### DSH (DeepSeek Harness)
- **负责**: 常规代码开发、测试、构建、bugfix
- **输出**: TypeScript 源码、测试文件、配置文件
- **不负责**: 架构决策、复杂设计、外部研究
- **工作区**: 整个项目 (除 `docs/` 下需要 Claude 决策的文件)

### Claude Code
- **负责**: 架构设计、接口定义、美术规范、技术文档
- **输出**: `docs/` 下的设计文档
- **不负责**: 具体编码实现
- **工作区**: `docs/` (自动任务限制)

### Grok Build
- **负责**: 外部数据调研、OSM 数据验证、许可核查
- **输出**: `docs/research/issue-<N>.md`
- **不负责**: 代码编写、架构设计
- **工作区**: `docs/research/` (自动任务限制)

### Codex
- **负责**: 复杂重构、性能优化、疑难 bug
- **输出**: TypeScript 源码 (高复杂度)
- **不负责**: 常规开发 (由 DSH 承担)
- **工作区**: `src/`, `tests/` (有额度限制)

## 协作最佳实践

1. **明确依赖**: 在 Issue 中用 `Depends-On: #N` 声明
2. **数据溯源**: 所有外部数据必须注明来源 URL
3. **接口先行**: 涉及多模块的改动先定义接口
4. **增量交付**: 小步快跑，避免大型 PR
5. **测试保护**: 每个 PR 必须通过自动测试
